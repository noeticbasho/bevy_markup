## Context

`tl` leaves character references as written, so the crate decodes them
itself: `template.rs` `decode_entities` (about 120 lines: numeric
references, the C1 → Windows-1252 table, longest-match named references)
over `src/entity_data.rs`, a 2,134-line table that
`scripts/generate_entities.py` generates from WHATWG's `entities.json`
(ADR 0027). It runs on every attribute value and text node the build
reads (about 20 call sites, plus tests).

It decodes only references closed by `;`. The spec, and so Chrome, also
decodes the ~100 legacy names without one (`&copy2` → "©2", `&notit;` →
"¬it;") and numeric references without one (`&#65` → "A"), with a
stricter rule inside attribute values (a legacy name followed by an
alphanumeric or `=` stays as written, so `?a=1&copy=2` in an `href`
survives).

ADR 0027 rejected an entity crate against the dependency policy
(AGENTS.md: "don't add unrelated crates"). The maintainer has since asked
for code the crate maintains to move to maintained dependencies where one
fits (the cleanup this ADR belongs to), and ADR 0035's trial ruled out
the bigger route — html5ever, which would have brought decoding with it —
on parse cost.

**htmlize** 1.1.0 (MIT/Apache-2.0) implements the spec's
character-reference algorithm: `unescape` for text and
`unescape_attribute` for attribute values, both returning `Cow<str>`
(borrowed when nothing changes). Two backends: `unescape` (the table in a
`phf` map) and `unescape_fast` (a generated byte matcher).

## Decision

1. Depend on `htmlize` with the `unescape` (`phf`) backend, and decode
   with it: `template.rs` keeps two thin functions, `decode_text` and
   `decode_attribute` (`impl Into<Cow<str>>` → `Cow<str>`, so a value
   with nothing to decode stays borrowed), and every call site uses the
   one for what it reads — text nodes and Markdown code use
   `decode_text`, attribute values `decode_attribute`. The trial measured
   the `unescape_fast` backend as fast on whole documents (it wins only on
   reference-dense values, which documents don't have) and 3.6 s slower
   to build clean.
2. Delete `decode_entities`, `terminated_digits`, `C1_REPLACEMENTS`,
   `src/entity_data.rs` and `scripts/generate_entities.py`. The decoder's
   unit tests become tests of the crate's contract (one level, unknown
   kept, the legacy and attribute rules) rather than restatements of the
   table.
3. Behaviour follows the spec where it didn't: legacy and unterminated
   numeric references decode, with the attribute exception. A new oracle
   vector, `character_references`, checks text as rendered and attribute
   values through attribute selectors, so Chrome confirms both rules.
4. AGENTS.md's dependency line records the relaxation: HTML-domain crates
   that replace code the crate maintains are in scope.

## Consequences

- 2,273 lines (net) leave `src/` and `scripts/` — the 2,134-line table,
  the decoder and the generator — for one dependency (`htmlize` and the
  `phf` runtime; `phf_codegen` at build time). The release binary carries
  a table either way (htmlize's adds about 220 KB to a minimal binary).
- Decoding matches the spec and Chrome, including the legacy forms the
  crate left verbatim. A template that relied on `&copy2` staying literal
  changes; none in the repository does.
- Call sites that decoded into a fresh `String` can now borrow when the
  value has no `&` (most class names, ids and text), and decoding is
  faster: 1.5× on plain values, about 11× on the escaped JSON in
  `data-with` / `data-l10n-args`, 1.8× over a whole 600-element page
  (trial report).
- The content lint's own five-escape decoder is gone too: it uses
  htmlize, so it reads text exactly as the crate does.
- Tree construction stays tag-soup (ADR 0035).
