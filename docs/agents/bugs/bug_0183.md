## Symptoms

**Fuzz css** times out (libFuzzer, 10 s per input) on an input of nested,
unclosed `light-dark(` calls: the shape bug_0179's paren bound
(`MAX_CSS_PAREN_NESTING` = 8) rejects. This input passes the pre-scan
and takes 0.6 s to parse in a release build (over 10 s under the
fuzzer's instrumentation). With its two `url(` renamed, the pre-scan
rejects it in 5 µs.

## Root cause

The pre-scan treats an unquoted `url(` as one token up to its `)`,
as cssparser does, so closers inside it close nothing. It decides that a
`url(` is that token by looking at the one byte before `url`: anything
but `[A-Za-z0-9_-]` or a non-ASCII byte starts a new name. cssparser
instead reads the whole name, and only a name whose value is `url`
(escapes decoded, ASCII case-insensitive) makes a URL token. The two
disagree whenever the byte before `url` is part of the name for
cssparser:

| text before `url(` | cssparser reads | the pre-scan read |
|---|---|---|
| NUL (the fuzz input) | the function `\u{FFFD}url(`: NUL is a name character, decoded to U+FFFD | a URL token |
| an escape, `\(` | the function `(url(` | a URL token |
| a hex escape, `\28 ` | the function `(url(` (the escape eats one space) | a URL token |

With no `)` after it, the pre-scan skips the rest of the text, and every
`(` after it goes uncounted. In release, each of the three takes 2.3 s to
parse with 24 nested `light-dark(` after the `url(`, where the pre-scan
rejects the same text without it in 3 µs. The reverse also exists:
`u\72l(` is a URL token for cssparser (its value is `url`), but the
pre-scan reads a function, so a `/*` inside it starts a comment the
tokenizer never sees: `u\72l(/*)` followed by the same 24 `light-dark(`
and a `*/` passes the pre-scan and parses for 3.6 s.

The same review of cssparser's tokenizer found a third gap: a string
ends at any CSS newline (`\n`, `\r`, form feed), but the pre-scan
ended one only at `\n`, so `"x\r` followed by the nesting hid it too.

## Fix

`nesting_over_limit` reads the tokens whose boundaries decide what a
`url(` is, as cssparser 0.37's `next_token` does:

- a name is read whole by `css_name` (cssparser's `consume_name`): ASCII
  name characters, NUL (as U+FFFD), non-ASCII, and escapes decoded by
  `css_escape` (up to six hex digits and one whitespace, or one
  character). It starts where `css_ident_start` (`is_ident_start`) says.
- a name followed by `(` is a URL token only when its value is `url`
  ASCII case-insensitively and the next non-whitespace (CSS whitespace,
  not Unicode's) isn't a quote; otherwise its `(` opens a block.
- hashes, at-keywords and numbers (`css_number_end`: sign, digits,
  fraction, exponent, then `%` or a unit name) are read whole, so `#url(`,
  `@url(` and `1url(` are a token and a plain `(`, never a URL; `<!--` is
  one token.
- strings end at `\n`, `\r` and form feed; an escaped `\r\n` continues
  one.

The URL body is skipped as before (to the first unescaped `)`), which is
where both cssparser's valid and bad URL tokens end.

`cssparser` (=0.37.0, already in the tree through lightningcss) is a
dev-dependency now: the property test builds text from the tokens that
open, close or hide blocks and checks that whatever cssparser nests past
a bound, the pre-scan rejects. Afterwards the four spellings above and the
CI timeout are rejected in under 10 µs; the CI css corpus (16,074 inputs)
has no input over 10 ms; no stylesheet of bevy_markup, vtuber or
prototype_19 is rejected.

## Minimal reproduction

```rust
// passes nesting_over_limit, then parses for ~2.3 s (release)
let css = format!("a{{color:\0url({}", "light-dark(".repeat(24));
// the same with `\\(url(` or `\\28 url(` in place of `\0url(`
```
