# bug_0200 — A huge pattern tile aborted the process

| field | value |
|---|---|
| ID | bug_0200 |
| Status | **fixed**: the render-cost estimate charges each pattern tile at its drawn size, so such a document is refused (`TooExpensive`) before drawing; upstream: UPSTREAM U36 |
| Severity | high (reachable from any SVG; an allocation failure aborts the whole app — `svg::guarded` can't catch an abort) |
| Component | `src/svg.rs` (`estimate_cost`, `CostWalk::path`) |
| Discovered by | `svg::tests::properties::hostile_magnitudes_never_panic` (a new proptest of generated documents), its first run: `memory allocation of 133170058088640 bytes failed` |
| Discovery agent | Claude Code session, `claude-opus-5-5` |
| Commit at discovery | `f43eb97` |
| Date | 2026-11-09 |
| Regression coverage | `svg::tests::pattern_tiles_count_toward_the_cost` (a 10⁶ px user-space tile, the find's box-unit tile scaled ×600, a nested tile at its outer tile's scale; ordinary tiles in both units still draw) |

## Symptoms

```xml
<pattern id='p' width='1e4' height='1e4' patternUnits='userSpaceOnUse'>
  <rect width='1' height='1'/></pattern>
<rect width='8' height='8' fill='url(#p)' transform='scale(100)'/>
```

The process aborted (`memory allocation of … bytes failed`) while
drawing: a 10⁶ × 10⁶ px tile.

## Root cause

resvg 0.49 `path.rs` `render_pattern_pixmap` allocates the tile as a
`Pixmap` of the pattern rect × the scale of the path's transform with
the pattern's, with no limit, and `Pixmap::new` allocates with
`vec![0; len]`, which aborts when the allocation fails (UPSTREAM U36).
`estimate_cost` walked the pattern's content but never charged the tile.

## Fix

`CostWalk::path` charges each pattern paint's tile area (×2: zeroed,
drawn into) at its drawn size (`path.abs_transform()` with the pattern's
transform, times the raster scale), refuses a non-finite tile, and walks
the content at the tile's scale, so nested patterns are charged at their
real size.
