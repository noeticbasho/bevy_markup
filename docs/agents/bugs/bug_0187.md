# bug_0187 — With `svg`, `BevyMarkupPlugin` replaced Bevy's `Assets<Image>` (and, with `svg-text`, `Assets<Font>`)

| field | value |
|---|---|

| Status | **fixed**: the plugin registers `Image` and `Font` only when no store exists |
| Severity | high (any full app built with `svg` and `DefaultPlugins` first: the image store's contents gone, and the next image load through an earlier handle panicked, index out of bounds in `Assets::insert`; with `svg-text`, Bevy's default font gone too) |
| Component | `src/lib.rs` (`BevyMarkupPlugin::build`) |
| Discovered by | the first run of the new `svg` example (ADR 0038 §10), `--offscreen`: a panic at startup |
| Discovery agent | Claude Code session, `claude-opus-5-5` |

## Symptoms

`cargo run --example svg --features svg-text,dev-tools -- --offscreen`
panicked in its first frames:

```text
thread 'main' panicked at bevy_asset-0.20.0/src/assets.rs:149:38:
index out of bounds: the len is 1 but the index is 5
  3: Assets<Image>::insert_with_index
  4: <Image as AssetContainer>::insert
  5: AssetInfos::process_asset_load
```

## Root cause

`App::init_asset::<A>()` (bevy_asset 0.20 `lib.rs`) isn't idempotent. It
creates a new `Assets::<A>::default()`, registers its fresh handle
allocator with the asset server, and inserts it, replacing any existing
store. Step 1 added `init_asset::<Image>()` to the plugin, so the `svg`
loader's asset type was registered in apps without `ImagePlugin`.
Part A (`svg-text`) did the same for `Font`.

In a real app `ImagePlugin` (and `TextPlugin`) run first. The plugin's
call then dropped every image Bevy had stored, and orphaned the handles
already given out: a load finishing through one inserted at its old
index into the new, shorter storage, and panicked. The headless tests
never had handles out when the plugin was added.

## Fix

`init_asset_once::<A>` registers the asset only when no `Assets<A>`
exists, for `Image` (`svg`) and `Font` (`svg-text`).
