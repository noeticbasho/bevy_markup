## Symptoms

A 1 248-byte inline document (a `<use>` fan-out of 10⁵ rects, inside the
work budget, plus an `feTurbulence` the cost estimate refuses), three
calls of `InlineSvgs::image`, release:

| call | result | time |
|---|---|---|
| 1 | `None` | 552 ms |
| 2 | `None` | 499 ms |
| 3 | `None` | 480 ms |

The same document without the filter: `Some`, then 1.5 µs per call. A
build is any content update or restyle of the UI — a `:hover` flip, a
context change — so each one stalls the main thread again. An accepted
document can stall its first build as long.

## Root cause

`InlineSvgs::image` inserts a cache entry only on success; each early
`return None` (parse error, `TooExpensive`, failed draw;
`svg.rs:857-884`) leaves nothing, so the next build converts again. The
parse is synchronous for any text up to `INLINE_SYNC_BYTES` (64 KB):
only the *draw* is gated by cost (`INLINE_SYNC_COST`), and the
conversion may take all of `MAX_SVG_WORK`. `svg.rs`'s module docs and
README say a costly inline document is drawn "on a background task"; its
parse isn't (review_0007 K18).

## Fix (proposed)

Cache the refusal under the same key (aged out like a success); send a
document whose `Bounds::work` exceeds a small threshold to the task, as
large text already goes.
