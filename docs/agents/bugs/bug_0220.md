## Symptoms

Two nested loops over `range` in a 92-byte template render n²
characters. Probed linear in the output (1 200² = 1.44 MB: 62 ms to
settle), so Tera's maximum `range` (100 000) nested twice is ~10 GB.

## Root cause

Tera caps component recursion (20) and `range` (100 000), not output,
and the render doesn't cap it either. The crate otherwise bounds Tera
operators (bug_0182), CSS nesting, DOM depth, grid tracks and SVG as if
templates and stylesheets were hostile, and the fuzz targets enforce
that; the README promises it only for SVG files. Nothing records which
inputs are untrusted, so this item, bug_0213 and bug_0209 are defects
only if templates and CSS may come from mods.

## Fix proposed by the review

An ADR stating the threat model per input (FTL and SVG untrusted; CSS
and templates: decide), then either a rendered-size cap (fail the
render past N bytes) or a sentence in the docs.

## Fix

Templates are untrusted (ADR 0044). Tera has no hook for a render budget
(UPSTREAM U39), so `src/tera_check/` ports Tera 2.4's lexer (nom) and
parser and runs an abstract render over bounds at load, after Tera
compiles the set: steps, the size of every built value and copies of
context data, per element of the app's data, with `set_global` growth in
loops checked symbolically. A template past `MAX_TEMPLATE_STEPS`,
`MAX_TEMPLATE_VALUE_BYTES` or `MAX_TEMPLATE_APP_COPIES`, or one the
check can't read, fails to load. `HtmlTemplate::render_source` also
renders through a writer refused past `template::MAX_RENDERED_BYTES` (16
MiB). A vendored Tera with run-time limits was tried first and dropped
(ADR 0044's alternatives). Beyond the review's nested loops, the session
probed `set_global` doubling (2²⁴ bytes in 5 ms; forty iterations abort
the process) and self-nested lists.
