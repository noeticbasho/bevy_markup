| field | value |
|---|---|
| ID | bug_0226 |
| Status | **fixed** (the commit after `4af00b9`) |
| Severity | high (DoS: reachable from any template with a context string, list or number > 1; ~100-byte templates stall the app) |
| Component | `src/tera_check/analysis.rs` (loop counts, ADR 0044) |
| Discovered by | [review_0008](../reviews/review_0008.md) L04 (a probe) |
| Discovery agent | Claude Code session, `claude-fable-5-2` |
| Commit at discovery | `54bad82` |
| Date | 2026-11-12 |
| Regression coverage | `review_0008_probes` (three nested loops over one list, a second loop over the same element's data, a comprehension over context data inside a loop over it: `NestedAppLoops`; `range(end=hp)` nested: `TooManySteps`; nested loops over each element's own data, filtered, accepted; falsified by counting a context `range` once) |

## Symptoms

Release build; nothing is printed, so `MAX_RENDERED_BYTES` never
applies:

| context value | levels | template | check: steps | render |
|---|---|---|---|---|
| list of 30 | 4 | 132 B | 16 | 7.5 ms |
| list of 30 | 5 | 165 B | 20 | 223 ms |
| 33-char string | 5 | 165 B | 20 | 513 ms |
| `hp = 100`, `range(end=hp)` | 3 | 123 B | 15 | 36.7 ms |
| `hp = 100`, `range(end=hp)` | 4 | 164 B | 20 | 3.54 s |
| list of 30 | 30 | 990 B | 120 | not rendered |

Each level multiplies the time by n: six levels over the list would be
about 7 s, five of `range(end=hp)` about 6 minutes. Tera's parser allows
40 levels.

## Root cause

A loop over an app value has the count `items.fold()`: one. That is ADR
0044's "per app element" accounting, but nested loops stay at one per
level, so n items cost n^levels while the check reports a handful of
steps. `range(end=x)` with a context number `x` counts once too
(`k.min(1)`), though a number isn't a collection the app sized.
`accepted_templates_render_within_the_bound` generates context lists of
at most one element, so it can't see this. Even at one level, the budget
is per element: a template may spend the whole step budget (0.45 s by
the ADR's calibration) for each of the app's rows.

## Fix

Values carry the app loop whose element they're part of (`Av::origin`,
kept through attributes, items and filters). A loop or comprehension
over app data inside another runs only over the innermost app loop's
element (`for card in group.cards`), so the work stays linear in the
app's data; anything else is refused with the new
`CheckError::NestedAppLoops`, whose message says to nest the data
instead. A `range` whose bound comes from the context counts as
`RANGE_MAX` items (ADR 0046).
