## Symptoms

```xml
<filter id='f'><feTurbulence baseFrequency='1e40'/></filter>
<rect width='8' height='8' filter='url(#f)'/>
```

`called Option::unwrap() on a None value` in usvg's
`parser/filter.rs`, in debug and release builds. `svg::guarded` caught it
(the load failed as `SvgError::Panicked`), but libFuzzer counts any panic
as a crash.

## Root cause

usvg 0.49's `convert_turbulence` reads `baseFrequency` as an `f32` list.
A number past `f32::MAX` (but within `f64`) becomes infinity. usvg checks
only `is_sign_positive()` and then unwraps `PositiveF32::new(x)`, which is
`None` for infinity.

## Fix

`svg_bounds::bounds` first runs `check_values`: an `feTurbulence` whose
own `baseFrequency` holds a number that isn't finite as `f32` fails with
`SvgError::OutOfRange` ("<feTurbulence> has an out-of-range
baseFrequency …: its numbers must be finite"). Only the attribute counts:
it isn't a presentation attribute, so usvg never takes it from CSS. A
number past `f64` fails svgtypes' parse, and usvg ignores the attribute,
so it isn't refused. The check is broader than the panic (it also refuses
a non-finite entry in a list usvg would ignore, e.g. after a negative
one); nobody writes such frequencies.

Large finite frequencies (`1e20`) pass the check and reach resvg's
turbulence, where they overflow an `i32` in debug builds: that's UPSTREAM
U20, caught by `guarded`, debug-only, and excused by the `svg` fuzz target.
