# bug_0170 — Content that changes height above the band shifts the visible rows for one frame

## Root cause
A content build culls with the heights the last layout measured. A
changed subtree's new height exists only after this frame's layout, so
the cursor places everything below it by the old height. Text changes do
it, and so do row insertions and removals inside a container (the
container's stored height is the old one). A root width change is the
same in its first frame (every height is the old width's), and so is an
inserted element whose height differs from its siblings' mean (ADR 0033:
the cursor estimates a new element's height instead of building every
row after it — bug_0168). Up to the band's
margin (one viewport by default) nothing visible changes; past it the
viewport's rows are culled for that frame. A known limit, not fixed:
invalidating the cursor after every changed row would build the whole
remainder of the document per text change (the bug_0168 cost on every
edit). A real fix needs the new heights before layout (an estimate per
changed row) or a second layout pass in the frame.

## Decision (2026-10-19)

Kept as a known limit, by the project owner's choice among three options:

- **Keep as a known limit (chosen).**
- **A second UI pass:** on frames that placed rows by stale or estimated
  heights, rebuild and re-run Bevy's UI chain after the measurement.
  Bevy 0.20's systems are public (`ui_layout_system`,
  `measure_text_system`, `text_system`, `update_clipping_system`,
  `ui_stack_system`), but about fifteen of them across `UiSystems::Prepare`
  to `Stack`, plus the crate's own sizing systems, would need re-running.
  That ties the crate to Bevy's internal UI schedule, which changes
  between versions, and doubles layout cost on those frames.
- **Shrinking it:** e.g. widening the band after a content change. It
  would still be possible past the margin.

Measuring changed text before layout would reimplement Bevy's text
measurement. The limit stays documented in `HtmlWindowed`'s docs; the
band's margin (one viewport by default) absorbs most changes; the next
frame corrects it. The windowing property exempts exactly that frame.
