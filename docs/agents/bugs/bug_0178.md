## Symptoms

Converting certain `.md` templates aborted the process (a Rust panic,
SIGABRT under the fuzzing runtime):

```
thread '…' panicked at pulldown-cmark-0.13.4/src/parse.rs:2199:47:
called `Option::unwrap()` on a `None` value
```

In an app, any `.md` template asset with such content panics at load, in
the load-time Markdown conversion (ADR 0020). Markdown in Fluent values
(`md::to_html`) is not affected: it uses pulldown-cmark's plain iterator,
which does not panic on these inputs; only the offset iterator does.

## Discovery

A 25-second honggfuzz run of the `html` target
(`scripts/fuzz-honggfuzz.sh html 25`) reported `crashes_count: 24` and
saved one crash file (`hfuzz_workspace/html/SIGABRT.PC.7ffff7a9a11c….fuzz`,
128 bytes). Replayed through the libFuzzer build (`cargo +nightly fuzz run
html <file>`), it panics as above; `cargo fuzz tmin` minimized it to 9
bytes: `+\t[<]:\xda\n\x0b`. The harness decodes bytes lossily, so `0xda`
becomes U+FFFD. A temporary probe showed the panic comes from
`dedent_blocks`, which asks pulldown-cmark for code ranges
(`into_offset_iter()`) on the template source as given.

## Minimal reproduction

Against pulldown-cmark alone (no options needed):

```rust
use pulldown_cmark::{Options, Parser};
// panics on 0.13.4; fine on 0.13.5
Parser::new_ext("- [a]: b\n\u{0B}", Options::empty()).into_offset_iter().count();
```

A list item whose only content is a link reference definition, followed
by a line holding only a vertical tab (U+000B) or form feed (U+000C).
Bullet and ordered lists panic (`- `, `* `, `+\t`, `1. `); the same
definition in a block quote (`> [a]: b\n\u{0B}`) or at the top level does
not, since only list paragraphs are tight. `Parser::new_ext(...).count()`
(the plain iterator) does not panic on any of these.

| pulldown-cmark | `iter` | `into_offset_iter` |
|---|---|---|
| 0.13.4 (bevy_markup's lock at discovery) | ok | **panic** |
| `96201943db` (0.13 branch, before #1021's cherry-pick) | ok | **panic** |
| `078feb520e` (0.13 branch, #1021 cherry-picked) | ok | ok |
| 0.13.5 | ok | ok |

## Root cause (upstream)

Read from the code, not traced in a debugger: the item's paragraph is
"tight" (inside a list) and, once the reference definition is taken out,
empty; the whitespace-only line after it keeps it as a paragraph node
without children (the block quote and top-level cases, whose paragraphs
are not tight, don't panic, which fits). `OffsetIter::next` skips tight
paragraphs by stepping into their children (`tree.push()` then
`tree.cur().unwrap()`), which assumes there is one. Upstream's PR #1021
("Correctly parse all-spaces line between refdef and paragraph", fixing
#997) changed how a whitespace-only line after a reference definition is
parsed, so the empty paragraph no longer arises; it is in 0.13.5
(cherry-pick `078feb520e`). The `unwrap()` itself is still on upstream
`main` (2026-10-23), so an empty tight paragraph reached another way would
panic again; #1084 is a different input reaching the same `unwrap()`
(also fixed for its input).

## Fix

`Cargo.toml`: `pulldown-cmark = "0.13.5"` (was `"0.13.3"`, locked at
0.13.4), so no build can resolve an affected version; all five lockfiles
(root, `fuzz/`, `honggfuzz/`, `fuzzcheck/`, `test-fuzz/`) updated with
`cargo update -p pulldown-cmark --precise 0.13.5`. The three driver
lockfiles (`honggfuzz/`, `fuzzcheck/`, `test-fuzz/`) were also stale
(bevy_markup 0.6.0, no `hotpath`), which cargo already rewrote on every
driver build; the update brings them current.

The full suite passes on 0.13.5 (474 tests under nextest, the
`fuzzing`-feature unit tests, doc tests, and the corpus replay), so the
other fixes cherry-picked into 0.13.5 change nothing bevy_markup tests.
