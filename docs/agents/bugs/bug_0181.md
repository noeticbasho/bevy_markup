## Symptoms

The CI failure above. Locally the same test passed narrowly (7.6×), so it
showed on the slower runner only. Build time per doubling of a sibling
list under `.hot ~ p` (no `.hot` present), best of three, debug build:

| Siblings | Before | After | No sibling rule |
|---|---|---|---|
| 400 | 31.3 ms | 25.6 ms | 26.5 ms |
| 800 | 60.8 ms (×1.94) | 39.8 ms (×1.55) | 39.9 ms (×1.51) |
| 1,600 | 154.2 ms (×2.54) | 67.9 ms (×1.71) | 68.3 ms (×1.71) |
| 3,200 | 461.0 ms (×2.99) | 123.7 ms (×1.82) | 122.6 ms (×1.79) |
| 6,400 | 1,584 ms (×3.44) | 236.2 ms (×1.91) | 232.5 ms (×1.90) |

The ratio per doubling climbing toward 4 is the quadratic term; after the
fix the curve matches the one with no sibling rule. With a `.hot` first
in the list (every element matches) it is the same: 234 ms at 6,400.

## Root cause

For `X ~ subject`, parcel's matcher (ADR 0034) walks back through every
preceding sibling of each element until one matches `X`. Over a list
with no match that is n²/2 sibling tests. The pre-ADR-0034 matcher did
the same (`siblings.iter().find(…)` per element), but its per-step cost
was small enough that the test's linear work hid the quadratic term — the
test's own comment notes "linear costs hide the quadratic". The engine's
heavier step (a `Node` per sibling, the `Element` trait calls) brought it
above the bound on CI.

## Fix

The answer to "does a sibling before index *i* match `X`" is
"the first entry matching `X` is before *i*", and that first entry is the
same for every element of the list. So:

- `Selector::from_parsed` records, for the `X ~ subject` shape whose `X`
  reads only the sibling itself (no combinator left of `X`, no `:is()` &
  co. with combinators inside it), the match-order offset of `X`, and
  gives each selector an id.
- `SiblingList` keeps a forward scan per (selector id, either-way mode):
  how far it has looked and the first match. `any_before(count)` resumes
  the scan only up to `count` and stops at the first match, so a whole
  list costs at most one `X` test per entry. The entries are fixed
  snapshots, so a scan stays valid for the list's life.
- `Selector::run` matches the subject's own compound
  (`matches_compound_selector_from`), then answers the sibling part from
  the scan. Without a threaded list (tests, image runs) it falls back to
  the engine, as do the shapes above that read context.

**Two mistakes caught on the way**, both by existing tests:
`matches_compound_selector_from` counts its offset in parse order (left
to right; `matches_selector`'s counts in match order), and a match of the
rightmost compound reads `FullyMatched`, not `Matched`. The first failed
`cascade::tests::sibling_combinators_match_preceding_siblings`; the second
`tests/selector_model.rs` (`p.b:not(:hover):first-child ~
.b[data-m]:nth-child(2)` matched an element whose only preceding sibling
didn't match `X`; seeds recorded).
