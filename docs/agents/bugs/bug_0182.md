## Symptoms

**Coverage per testing layer** aborts in the fuzz-corpus replay:

```
thread 'replay_html_corpus' has overflowed its stack
fatal runtime error: stack overflow, aborting
```

All 16 offending corpus inputs (527–822 bytes) are one `{{ … }}` holding
a chain of 140–200 binary operators, e.g. `{{n-3.-n%Qabs%none%Q%zGf…`.
The abort is a `SIGABRT`, not a panic: no error reaches the caller, and
the whole process ends. The `html` fuzz target itself doesn't fail: it
runs optimized, where the same inputs fit the stack.

## Root cause

Tera's parser builds a left-associative chain (`a - b - c …`, `a | f | g
…`, `a.b.c …`) in a loop, but its compiler walks the resulting left-deep
AST recursively, one `compile_expr` frame per operator (137 frames in the
backtrace of a 150-operator chain). Tera 2.4.0 bounds this with
`MAX_EXPRESSION_COMPLEXITY` = 256 operations per expression (its fix for
[Keats/tera#1035](https://github.com/Keats/tera/issues/1035)), a bound
sized for an 8 MB main thread. On a 2 MB thread, the size of Rust's
spawned threads, the libtest threads and Bevy's task pool threads, a
debug build overflows first:

| chain `{{ n - n - … }}` on a 2 MB thread | debug | release |
|---|---|---|
| 135 operators | ok | ok |
| 136 operators | stack overflow | ok |
| 256 operators (Tera's cap) | stack overflow | ok |
| 260 operators | — | "The expression is too complex" |

Every operator kind shows it in debug (`+`, `~`, `| upper`, measured at
140); release build survives all of them up to the cap (`-`, `+`, `~`,
`and`, `|` filters with and without arguments, `.x`, `[0]`, nested
parentheses).

## Minimal reproduction

```rust
// debug build, on a 2 MB thread (any #[test]): aborts the process
let template = format!("{{{{ n{} }}}}", " - n".repeat(136));
bevy_markup::template::new_tera().add_raw_template("t.html", &template);
```
