| Component | `src/canvas.rs` (`sync_canvases`), `src/build.rs` (`update_spec`) |
| Discovered by | [review_0007](../reviews/review_0007.md) K12 (a probe) |
| Discovery agent | Claude Code session, `claude-fable-5-2` |
| Commit at discovery | `f76b320` |
| Date | 2026-11-11 |
| Regression coverage | `tests/canvas.rs` `a_framed_canvas_keeps_its_frame_and_its_picture` (falsified twice: the image on the element, and the picture not kept by updates — then respawned, a different entity); the binding tests read the picture (`picture`/`viewport`/`shown_image` helpers) |

## Symptoms

`canvas.framed { border-image: url(frame.png) 4 stretch; border-width:
4px }` with a `CanvasSource::Image`:

| moment | the element's `ImageNode` |
|---|---|
| before binding | `frame.png`, sliced |
| bound | the canvas image, stretched (the frame is gone) |
| after an in-place update (a class change) | `frame.png`, sliced (the picture is gone; `showing` still says `Image`) |

A camera canvas keeps its `ViewportNode` but shares the element with the
frame, whose center Bevy always draws.

## Root cause

An image canvas is an `ImageNode` on the element (`CanvasImage`); CSS
`border-image`/`background-image` is an `ImageNode` on the same element
(`CssFrame`). `sync_canvases` overwrites the frame when it binds;
`update_spec` re-inserts the frame on every update (`ImageNode` has no
`PartialEq`), and `sync_canvases` then sees `has_image` and an unchanged
`showing`, so it doesn't bind again.

## Fix proposed by the review

Show the source on a child node the canvas owns (the frame stays on the
element), or document that a canvas takes no CSS image and drop the
declaration with a warning.

## Fix

The source shows on a `CanvasPicture` child (in the prelude) filling the
canvas's padding box: `ViewportNode` or a stretched `ImageNode` go
there, never on the element, which keeps its CSS
`border-image`/`background-image`. The build's `Tree` query treats the
picture like an app-nested `HtmlUi` (`update_children` keeps it,
`same_identity` never pairs it, `refresh_cached_handles` skips it).
`sync_canvases`' `bind` spawns the picture on demand, puts a viewport on
it only once it's laid out at a non-zero size (Bevy's resize would make
the image 1 × 1), and despawns it when the canvas shows nothing. Of the
review's two directions this keeps both features; the canvas feature is
unreleased, so moving the components is no break for users. ADR 0043 records the choice.
