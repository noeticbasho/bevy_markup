## Symptoms

Parsing FTL with deeply nested placeables (`x = {{{…"a"…}}}`) aborts the
process with `thread '…' has overflowed its stack`. In a p23 app the parser
runs inside bevy_fluent's bundle loader on a task-pool thread, so a crafted
or corrupted translation file of a few KB crashes the app.

## Discovery

Replaying the cargo-fuzz `ftl` corpus through `p23::fuzz::translate` in a
debug test aborted on stack overflow. The corpus held inputs nesting
placeables up to 1053 levels deep (in ~1.1 KB). libFuzzer never flagged
them: it runs an optimized build on the 8 MB main thread, where that depth
fits.

## Minimal reproduction

```rust
let ftl = format!("x = {}\"a\"{}\n", "{".repeat(depth), "}".repeat(depth));
fluent::FluentResource::try_new(ftl); // stack overflow for large `depth`
```

Overflow depth (parse alone; formatting adds nothing on top), measured:

| build | 2 MB stack (spawned thread) | 8 MB stack (main thread) |
|---|---|---|
| debug | 200–400 | 800–1600 |
| release | 1600–3200 | 6400–12800 |

## Root cause

fluent-syntax parses placeables and inline expressions recursively, with no
nesting limit.

## Fix

Every recursion path (placeable → expression → inline expression or select
variant → placeable) goes through `Parser::get_placeable`, for both `parse`
and `parse_runtime` (which fluent-bundle uses). The vendored parser now
counts nesting there and returns the new `ErrorKind::PlaceableNestingTooDeep`
past `MAX_PLACEABLE_DEPTH` = 100 (`vendor/fluent-syntax/src/parser/core.rs`,
marked `PATCH(p23)`). The entry becomes Junk and parsing resumes at the next
entry, like any other parse error. 100 keeps a ≥ 2× margin under the
smallest overflow depth measured (debug, 2 MB stack); real translations nest
a handful of levels. No dependent matches `ErrorKind` exhaustively, so the
new variant breaks nothing.

Checked: with the limit set to `usize::MAX` the regression test aborts with
the original stack overflow. Still to do: report upstream.

## Update (2026-10-05): the first fix missed nested calls

The vendored fix counted placeables in `get_placeable`. Function calls
nest without placeables, through call arguments: inline expression → call
arguments → inline expression (`x = { F(F(F(…1…))) }`). That overflowed the
stack even with the vendored fix, at depth 1000 (debug, 2 MB stack);
unpatched, between 100 and 400 levels.

Both cycles pass through `get_inline_expression` once per level, so the fork
counts depth there (`MAX_NESTING_DEPTH` = 100, new
`ErrorKind::NestingTooDeep`). Boundaries, derived by hand: n nested braces
are n inline expressions (100 parse, 101 fail); n calls in a placeable are
n + 1 (99 parse, 100 fail). `vendor/fluent-syntax` is gone; all five
manifests patch fluent-syntax from the fork's git branch.

## Update: a load-time check instead of the fork

Since 2026-11-11 (ADR 0045) the fork is no longer wired in: `ftl_check`
ports fluent-syntax's `parse_runtime` and refuses a resource nesting
placeables, select variants or call arguments past `MAX_FTL_NESTING`
(64) at load. The fork counted only in `get_inline_expression`, which
the select-variant cycle doesn't pass through; the port counts every `{`
and `(` level. Regression:
`fuzz::tests::deeply_nested_expressions_are_an_error_not_a_stack_overflow`,
`nesting_up_to_the_limit_still_works`,
`ftl_check::tests::{nesting_is_bounded_on_every_cycle,
the_limit_fits_a_two_megabyte_stack,
the_port_finds_fluent_syntaxs_entries}`.
