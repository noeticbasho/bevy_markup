## Symptoms

Through the real loader, in a release build, 24 template files, each
holding 30 nested `{% for a in items %}` around an `{% include %}` of the
next (23.6 KB in all), abort the app:

```
thread 'IO Task Pool (1)' has overflowed its stack
fatal runtime error: stack overflow, aborting   (SIGABRT)
```

`tera_check::check` alone on a 2 MB thread:

| build | accepted | overflows |
|---|---|---|
| release | 16 files × 30 levels | 24 × 30 |
| debug | 2 × 39 | 4 × 39 (5 KB), 8 × 20 |

Tera itself compiles and renders 60 files × 38 levels on the same
thread. At `f76b320` (before the check) these templates loaded.

## Root cause

`Analyzer` recurses once per statement level (`nodes` → `for_loop` →
`nodes` …) and continues into each `{% include %}`. `MAX_NESTING` (64)
counts templates and components only, while Tera allows 40 statement
levels in each. Bevy's IO task pool threads have the default 2 MB stack.
`the_check_bounds_its_own_work` tests a chain of 200 includes with
nothing nested in them, so the product of the two depths is untested.

## Fix

One depth budget, `analysis::MAX_DEPTH` (96), counts every level the
analysis recurses through — statement lists and expressions, so
includes, component bodies, captures and loops all count — and refuses
past it with `TooComplex`. A level costs about 14 KB of a debug build's
stack (measured with a stack-pointer probe on a 256 MB thread), so 96
take 1.4 MB of the asset thread's 2 MB. Real templates nest a few
levels; Tera allows 40 per file.
