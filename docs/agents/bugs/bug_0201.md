## Symptoms

```xml
<filter id='f' primitiveUnits='objectBoundingBox'><feFlood width='4e5'/></filter>
<rect width='6000' height='10' filter='url(#f)'/>
```

`called Option::unwrap() on a None value` in tiny-skia-path 0.12.0
`rect.rs:707` (`NonZeroRect::to_int_rect`). An `feOffset dx='1e8'` under
`scale(200)` panicked in `size.rs:88` (`IntSize::to_int_rect`) instead.

## Root cause

resvg 0.49's `filter/mod.rs` `apply_inner` converts the filter region and
each primitive subregion to pixels with `NonZeroRect::to_int_rect`, and
`apply_offset`/`apply_drop_shadow` saturate the scaled offset to `i32` for
`draw_pixmap`, which calls `IntSize::to_int_rect(x, y)`. Both unwrap
`IntRect::from_xywh`, which is `None` when `x + width` passes `i32::MAX`
(UPSTREAM U35).

## Fix

`check_extent`'s walk (through the transforms resvg applies) maps each
filter region and subregion to pixels and scales each offset as resvg's
`scale_coordinates` does; anything past `MAX_SVG_FILTER_REGION` refuses.
2²⁴ px is 128 × `MAX_SVG_EXTENT` (room for regions around large blurred
shapes) and far below the overflow. Some refused regions wouldn't have
panicked (resvg skips a group whose layer can't be allocated before it
converts the region): a harmless over-refusal of absurd documents.
