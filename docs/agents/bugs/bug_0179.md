## Symptoms

Two nightly jobs failed every night for two weeks:

- **Fuzz css** timed out (libFuzzer, 10 s per input) on inputs of nested
  `light-dark(`, e.g. `timeout-849f2243…` (820 bytes) and
  `slow-unit-abee3a3c…` (664 bytes).
- **Coverage per testing layer** aborted in `replay_css_corpus`
  (`thread 'replay_css_corpus' has overflowed its stack`) on a CI corpus
  input that nests `[` 505 deep.

In an app, the first is real: a stylesheet with ~30 nested `light-dark(`
takes minutes to load, ~30 nested `calc(` around a `var()` hours, and the
existing pre-scan (bug_0092, bug_0106: 32 blocks) let both through. A
`var()` chain could also assemble such a value and re-parse it per
element. The second was a harness gap: `fuzz::cascade` parsed without the
loader's pre-scan, so the fuzzer and the replay tested inputs every app
already rejects.

## Root cause

lightningcss re-parses some functions' arguments after a failed typed
parse, so its time doubles per nesting level:

| depth | unclosed `light-dark(` | `--x:` nested `light-dark(var(--a))` | nested `calc(var(--x) - 1px)` |
|---|---|---|---|
| 8 | 0.05 ms | 0.08 ms | 0.27 ms |
| 12 | 0.58 ms | 1.13 ms | 5.9 ms |
| 16 | 9.0 ms | 17.8 ms | 124 ms |
| 18 | 36 ms | 72 ms | 554 ms |

(release build, lightningcss 1.0.0-alpha.72 alone, this machine.) Upstream
issues: [#1382](https://github.com/parcel-bundler/lightningcss/issues/1382)
(light-dark; fix PR [#1383](https://github.com/parcel-bundler/lightningcss/pull/1383)
open) and [#1389](https://github.com/parcel-bundler/lightningcss/issues/1389)
(calc with var). The stack overflow is lightningcss's unbounded recursion
([#1297](https://github.com/parcel-bundler/lightningcss/issues/1297),
[#1155](https://github.com/parcel-bundler/lightningcss/issues/1155),
[#1092](https://github.com/parcel-bundler/lightningcss/issues/1092)):
in a debug build ~500 nested blocks overflow a 2 MB thread, in release
~3000 nested `calc(` or `light-dark(`.

## Fix

- `nesting_over_limit` also bounds `(…)` blocks alone at
  `MAX_CSS_PAREN_NESTING` = 8 (authored values nest ~4; the studio's CSS
  at most 2). The worst case at 8 is ~0.3 ms per declaration. The block
  bound (32) stays. The function lost its `limit` parameter: every caller
  (loader, `style=`, substituted values) uses both bounds.
- A `var()` chain whose substituted value nests deeper than 8 parens is
  dropped before the re-parse: `var_function_nesting_is_capped` now
  checks 4 links × 2 `calc(` resolve and 4 × 3 drop (it used 4 × 7 = 28
  under the old bound).
- `fuzz::cascade` applies the pre-scan first, like the loader.

After the fix the two CI timeout inputs run in 0 ms in the css target,
and the full replay including the CI corpus (23 359 css inputs) passes in
3.4 s.

## Minimal reproduction

```rust
// a stylesheet that took minutes to load before the fix
format!("p {{ color: {} }}", "light-dark(".repeat(30));
// hours: calc(calc(…calc(var(--x) - 1px)…) - 1px), 30 deep
(0..30).fold("var(--x)".to_owned(), |v, _| format!("calc({v} - 1px)"));
```
